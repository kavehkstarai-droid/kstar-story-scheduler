# ناشر قسمت‌های آمادهٔ کاوه استار

ناشر در مخزن عمومی `kavehkstarai-droid/kstar-story-scheduler` مستقر و فعال است. قسمت ۰۱ با [رسید ۱۳۵۹](https://t.me/KavehStar/1359) منتشر شده و در تاریخچه ثبت است؛ در زمان این به‌روزرسانی ویدیوی تازه‌ای در صف نیست. مقصد داخل کد ثابت است: **@KavehStar**. این نسخه ویدیوی جدید تولید نمی‌کند، خرید نمی‌کند و قسمت قدیمی را دوباره وارد صف نمی‌کند.

فقط فایل‌هایی منتشر می‌شوند که قبلاً ساخته و بازبینی شده‌اند. دو منبع مجاز است: `file_id` فایلی که با **همان بات** در تلگرام بارگذاری شده، یا MP4 در بخش Releases همین مخزن. توکن بات فعلی متعلق به `IQ7_bot_bot` است. ساخت قسمت‌ها با اعتبار موجود HeyGen در جلسهٔ تولید انجام می‌شود؛ فایل‌های آماده در فضای ابری می‌مانند و انتشار به روشن‌بودن لپ‌تاپ نیاز ندارد. تمام‌شدن صف باعث توقف می‌شود و تولید تازه‌ای را راه نمی‌اندازد.

برای ویدیوی آمادهٔ ذخیره‌شده در Releases، فیلد media به شکل زیر است؛ `size_bytes` و `video_sha256` باید از فایل نهایی واقعی ثبت شوند:

```json
{
  "release_url": "https://github.com/kavehkstarai-droid/kstar-story-scheduler/releases/download/story-batch-2026-09-28/Kaveh-Star-02-serial-1080p.mp4",
  "size_bytes": 12345678
}
```

عدد نمونهٔ بالا واقعی نیست. ناشر فقط URL انتشار همین مخزن را می‌پذیرد، فایل را قبل از رزرو ارسال دریافت می‌کند و اندازه و SHA-256 را تطبیق می‌دهد. تغییر فایل یا نشانی نامعتبر مانع ارسال می‌شود. فایل موقت پس از اجرا پاک می‌شود. این روش به خواندن هیچ پیام خصوصی یا پیش‌ارسال همهٔ قسمت‌ها به گروه نیاز ندارد.

## بررسی اختیاری دسترسی تولید ابری در آینده

این بررسی برای مسیر فعلیِ ساخت با اعتبار اشتراک و انتشار فایل آماده لازم نیست. Workflow دستی **Verify HeyGen API access (no generation)** فقط دسترسی و موجودی API را بررسی می‌کند. تولید ویدیو، خرید، شارژ، ارسال تلگرام یا خواندن پیام خصوصی ندارد. ناشر سه‌ساعته مستقل از این آزمون باقی می‌ماند.

برای اجرای آزمون، کلید API خودتان را فقط در Settings → Secrets and variables → Actions → New repository secret با نام `HEYGEN_API_KEY` قرار دهید. آن را در چت، کد یا فایل مخزن ننویسید. سپس در Actions همین workflow را از شاخهٔ اصلی اجرا کنید. برنامه فقط به نشانی ثابت `GET https://api.heygen.com/v3/users/me` درخواست می‌دهد؛ انتقال به نشانی دیگر را رد می‌کند و پروفایل یا کلید را در لاگ چاپ نمی‌کند.

فقط موجودی مثبت و معتبر کیف API با شارژ خودکارِ صریحاً خاموش، امکان ادامهٔ بررسی را نشان می‌دهد. موفقیت این آزمون به معنی فعال‌شدن تولید نیست؛ سازندهٔ ویدیو، کنترل صدای اصلی و کیفیت خروجی هنوز باید پیاده‌سازی و با یک خروجی واقعی آزمایش شوند. موجودی اشتراک وب جایگزین موجودی API نیست. اگر موجودی API کافی نباشد، شرط «بدون هزینهٔ جدید» مانع فعال‌سازی تولید پیوسته می‌شود.

طبق [راهنمای رسمی HeyGen CLI](https://github.com/heygen-com/heygen-cli#authenticate)، اجرای بدون حضور کاربر در CI از کلید API استفاده می‌کند؛ ورود OAuth برای کاربر حاضر است. [راهنمای قیمت‌گذاری API](https://help.heygen.com/en/articles/10060327-heygen-api-pricing-explained) نیز صورتحساب API را از اشتراک وب جدا می‌کند. نشست اتصال HeyGen داخل Codex یا مرورگر به GitHub منتقل نمی‌شود.

## راه‌اندازی در مخزن جدید عمومی

1. یک مخزن **جدید و عمومی** برای همین کار ایجاد کنید. محتوای این پوشه، شامل پوشهٔ مخفی `.github`، باید در ریشهٔ مخزن قرار بگیرد. مخزن موجود و نامرتبط را تغییر ندهید.
2. در Settings → Secrets and variables → Actions یک Repository secret با نام `TELEGRAM_BOT_TOKEN` ذخیره کنید. توکن را در کد، فایل صف، README، issue یا پیام عمومی نگذارید. `GITHUB_TOKEN` را GitHub به‌صورت خودکار فراهم می‌کند.
3. به Workflow اجازهٔ نوشتن محتوا بدهید تا بتواند فقط `state.json` را commit و push کند. محدودیت شاخهٔ پیش‌فرض نباید این commit را مسدود کند. اگر push رد شود، ارسال انجام نمی‌شود.
4. قسمت‌های بازبینی‌شده را طبق قالب پایین در `queue.json` اضافه کنید. برای مسیر `file_id`، فایل باید با همین بات از قبل بارگذاری شده باشد؛ `file_unique_id` را به جای `file_id` وارد نکنید. مسیر `release_url` فایل آمادهٔ همین مخزن را هنگام نوبت انتشار بارگذاری می‌کند.
5. ابتدا تست‌ها و `python3 publisher.py --check` را اجرا کنید. وقتی صف، مقصد و بات تأیید شد، `config.json` را به `{"enabled": true}` تغییر دهید و روی شاخهٔ پیش‌فرض commit کنید.
6. Workflow از منوی Actions قابل اجرای دستی است. اجرای دستی هم فاصلهٔ سه‌ساعته را دور نمی‌زند. این راه‌اندازی پس از استقرار به روشن‌بودن لپ‌تاپ نیاز ندارد.

زمان‌بندی بررسی صف: دقیقه‌های **۰۲، ۱۷، ۳۲ و ۴۷ هر ساعت** به وقت UTC. هر بار فقط وقتی حداقل **۱۰۸۰۰ ثانیه، یعنی سه ساعت** از ارسال موفق قبلی گذشته باشد، یک قسمت تازه منتشر می‌شود. بنابراین هدف، فاصلهٔ سه ساعت به‌علاوهٔ انتظار تا بررسی بعدی است؛ در حالت عادی انتظار بررسی حداکثر ۱۵ دقیقه است، ولی تأخیر خود GitHub می‌تواند بیشتر شود. ساعت دقیق انتشار تضمین‌شده نیست. اجرای دستی نیز همین محدودیت را رعایت می‌کند. بررسی پانزده‌دقیقه‌ای از جهش ناخواستهٔ فاصله به شش ساعت پس از تأخیر جلوگیری می‌کند.

فقط رویدادهای schedule و workflow_dispatch وجود دارند؛ Pull Request یا push به‌تنهایی ارسال راه نمی‌اندازد. اجرا به شاخهٔ پیش‌فرض محدود است. هم‌زمانی یک است و اجرای درحال‌انجام لغو نمی‌شود.

## هزینه و محدودهٔ عمومی‌بودن

Workflow از runner استاندارد `ubuntu-24.04` در مخزن عمومی استفاده می‌کند. طبق [مستندات GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions)، runner استاندارد برای مخزن عمومی رایگان است. runner بزرگ، مخزن خصوصی، ذخیرهٔ artifact/cache یا سرویس پولی دیگری در این بسته استفاده نمی‌شود. قبل از درخواست تلگرام، برنامه عمومی‌بودن مخزن و شاخهٔ پیش‌فرض را از API گیت‌هاب دوباره بررسی می‌کند؛ خطا یا خصوصی‌بودن باعث توقف می‌شود.

متن قسمت‌ها، شناسهٔ فایل تلگرام، سابقهٔ ارسال و ویدیوهای بخش Releases عمومی هستند. فقط محتوایی را اضافه کنید که برای انتشار عمومی آماده است. هیچ کلیدی همراه فایل‌ها قرار ندهید. ویدیو در تاریخچهٔ Git، artifact یا cache ذخیره نمی‌شود؛ نسخهٔ موقت هنگام اجرای ناشر دریافت و پاک می‌شود.

## قالب صف

این مثال را فقط با دادهٔ واقعی و تأییدشده جایگزین کنید؛ `reviewed: false` عمداً مانع انتشار آن است:

```json
{
  "version": 1,
  "episodes": [
    {
      "episode_id": "ep-002",
      "story_id": "kaveh-banner-002",
      "title": "عنوان قسمت آماده",
      "script": "متن کامل و نهایی روایت همین فایل",
      "telegram_caption": "کاوه استار | قسمت دوم\nبازآفرینی ادبی بر پایهٔ شاهنامهٔ فردوسی.\nمنبع و توضیح تأییدشدهٔ همین قسمت.",
      "video_sha256": "هش ۶۴رقمی واقعی فایل MP4",
      "reviewed": false,
      "media": {"file_id": "شناسه واقعی فایل بارگذاری‌شده با همین بات"}
    }
  ]
}
```

`episode_id` و `story_id` باید یکتا و با حروف لاتین، عدد، نقطه، خط تیره یا زیرخط باشند. `telegram_caption` متن کامل و تأییدشدهٔ همراه ویدیو، شامل توضیح بازآفرینی ادبی و منبع است؛ برنامه آن را عیناً و بدون کوتاه‌کردن می‌فرستد. این فیلد اجباری است و نباید از ۱۰۲۴ واحد UTF-16 بیشتر شود؛ بیشتر ایموجی‌ها دو واحد مصرف می‌کنند. تغییر نام قسمت، محتوای تکراری را مجاز نمی‌کند: هش متن نرمال‌شده و هش ویدیو نیز در صف و تمام سابقهٔ انتشار کنترل می‌شوند. نرمال‌سازی، فاصله‌های اضافی، نیم‌فاصله، علامت‌های جهت متن و تفاوت ک/ك و ی/ي را یکدست می‌کند؛ تشخیص شباهت معنایی خودکار نیست و موضوع تازه باید در بازبینی انسانی تأیید شود.

هش فایل MP4 در PowerShell:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\path\reviewed-video.mp4'
```

هش را با حروف کوچک در صف ثبت کنید. برای `release_url`، ناشر اندازه و هش فایل دانلودشده را کنترل می‌کند. ناشر `file_id` را دوباره دانلود نمی‌کند؛ در آن مسیر **مسئول آماده‌سازی باید تطبیق هش، فایل بارگذاری‌شده و متن را تأیید کند**. هش متن خودکار محاسبه می‌شود؛ برای ثبت اختیاری `script_sha256` می‌توانید اجرا کنید:

```text
python3 publisher.py --hash-script script.txt
```

ترتیب آرایه ترتیب انتشار است. اولین قسمت منتشرنشده اگر بازبینی نشده باشد، قسمت‌های بعدی هم منتشر نمی‌شوند. قسمت‌های قبلاً منتشرشده می‌توانند در صف بمانند؛ برنامه آن‌ها را رد می‌کند. **`state.json` را با خالی‌کردن صف یا شروع فصل تازه پاک نکنید**؛ حافظهٔ جلوگیری از تکرار در آن قرار دارد. وقتی صف تمام شود برنامه بی‌صدا خارج می‌شود.

## جلوگیری از ارسال تکراری

برای هر ارسال، برنامه ابتدا هویت قسمت را در `state.json.dispatching` رزرو می‌کند و آن را commit و **push** می‌کند. فقط بعد از موفقیت push، دقیقاً یک درخواست `sendVideo` انجام می‌شود. بعد از دریافت موفقیت قطعی، `message_id` و `sent_at` در `sent` ثبت و push می‌شوند و رزرو پاک می‌شود.

اگر درخواست timeout شود، فرایند پس از رزرو قطع شود یا ذخیرهٔ رسید شکست بخورد، رزرو باقی می‌ماند و **همهٔ ارسال‌های بعدی متوقف می‌شوند**. حتی خطای روشن تلگرام نیز در این نسخه بدون تلاش دوباره، نیازمند بررسی دستی است. این رفتار عمداً تحویل ناقص را به تکرار ناخواسته ترجیح می‌دهد.

برای رفع توقف:

1. ابتدا `enabled` را `false` کنید و مطمئن شوید هیچ اجرای فعال باقی نمانده است.
2. مقصد تلگرام و قسمت رزروشده را بررسی کنید. اگر وضعیت مبهم است، رزرو را پاک نکنید.
3. اگر ارسال انجام شده، چهار فیلد هویت از رزرو را همراه `message_id` واقعی و زمان ارسال `sent_at` به `sent` اضافه کنید؛ `last_sent_at` باید بزرگ‌ترین زمان در سابقه باشد. زمان‌ها عدد صحیح Unix بر حسب ثانیه هستند. سپس `dispatching` را `null` کنید.
4. فقط اگر با بررسی قطعی مشخص شد ارسال رخ نداده و هیچ درخواست درحال‌انجامی باقی نمانده است، می‌توان رزرو را پاک کرد و همان قسمت را برای نوبت بعد نگه داشت.
5. `--check` را اجرا کنید، اصلاح را روی شاخهٔ پیش‌فرض commit/push کنید و سپس دوباره فعال کنید.

کد توکن یا متن خطای شامل URL توکن‌دار را log نمی‌کند. هیچ مسیر retry خودکار برای `sendVideo` وجود ندارد. [مرجع رسمی Telegram Bot API](https://core.telegram.org/bots/api#sendvideo) توضیح می‌دهد که `file_id` برای استفادهٔ مجدد فایل است و این شناسه به بات مشخص وابسته است.

## بررسی محلی بدون ارسال

```text
python3 -m unittest discover -s tests -v
python3 publisher.py --check
```

تست‌ها فقط transport و state جعلی دارند و شبکه یا ارسال واقعی ندارند. تست‌ها ترتیب رزرو/ارسال، شکست persistence، timeout، قطع پس از رزرو، خطای ثبت رسید، فاصلهٔ سه ساعت، جلوگیری از تکرار، پایان صف، محدودیت مقصد و بررسی مخزن عمومی را پوشش می‌دهند. اجرای معمول برنامه در حالت فعال نیز بیرون از GitHub Actions مجاز نیست.
